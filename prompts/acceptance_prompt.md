# 独立教学验收 Agent (Acceptance Agent) 派发规范

本模板集中管理"独立教学验收 Agent"的派发提示词、两阶段输入边界、结论协议与返修接口。验收 Agent 的职责严格限定为**核对与退回**：不直接改写被验收的正文，不参与规划和写作，凭正文证据作判断。主 Agent 保留最终集成责任。

这里的"独立"指：未参与本次规划与写作、使用新上下文、凭学生实际可见内容作判断，并能退回有实质问题的产物。在原写作对话中追加"现在你是验收专家"，或把规划者的自评交给另一个 Agent 背书，均不满足独立性要求。

---

## 角色与触发时机

- `TypeName`: `"self"`
- `Model`: `"flash"`（必须显式指定，与其他执行子 Agent 一致；宿主适配层负责路由校验，不得自动回退到更贵模型）
- `Role`: `"独立教学验收专员"`
- **触发位置**：
  1. 开篇切片与首个实质任务（首节原型）完成时先运行一次，避免整章完成后才发现入口职责错误；
  2. 全部切片装配后，检查跨节接口、答案首次揭示位置与实例重访带来的新问题；未改变的内容不必全文重审；
  3. 首次采用新入口、改动依赖或反复返修时，可加派**学生视角试读**（仅需阶段一输入）；通常不必每节另派一个。
- **验收粒度**：按学习依赖划分的连贯片段，不按文件。开篇至少与首个实质任务一起读；禁止"一文件一验收者"式的机械切分，否则会漏掉跨文件答案前置。
- **版本责任**：验收结论绑定所审文件版本（记录相关文件的内容哈希或版本标识），验收记录保存为 `.pd/acceptance/<scope>.md`（含所审摘要、阶段一记录、结论与问题处理结果）。此后若改变题干、定义位置、答案揭示或跨节顺序，受影响部分重新进入验收，旧 PASS 自动失效（`deliver.py` 按摘要不一致拒绝交付）；纯排版修改只触发技术检查，但也要确认没有裁切内容、改变阅读顺序或破坏图文对应。
- **记录格式（供 deliver.py 机械核对）**：验收记录头部必须含如下字段行——
  ```text
  scope: <验收范围，如 sec0-sec1 或 chapter>
  conclusion: PASS | REVISE | NEEDS_EVIDENCE
  digest: <所审版本的 content_digest，取自 make_review_pack.py 输出的 manifest.json>
  ```
  REVISE / NEEDS_EVIDENCE 的处理结果以同一 scope 的后续记录追加：复验通过写新的 `conclusion: PASS` + 当前 `digest`；有依据撤销写 `withdrawn: <依据>`。

## 两阶段输入边界（主 Agent 负责上下文控制）

验收分两阶段执行，可由同一个新 Agent 顺序完成；阶段一记录固定后才进入阶段二。

### 阶段一：学生视角审读（先执行）

只提供：读者前置与用途、按实际阅读顺序排列的**学生可见内容**。不提供教师答案、作者自评、三张映射表或预期缺陷清单。

- 学生可见内容应取自 `scripts/make_review_pack.py` 生成的学生审读包（`.pd/review/`，含按页文本与所审版本摘要）；**不得把含 `\fillin[答案]`、`solution`、`teacherNote` 的 TeX 原样当作学生输入**。`pdftotext` 抽取的阅读顺序存疑时（双栏、图文混排），直接审读渲染页，不依据可能错序的文本补猜任务结构。
- 逐任务记录：完成该任务所需的动作、结果可依据的材料、尚缺的信息。先提交此记录。
- 不得用自己掌握的后续理论替学生补齐依赖。

### 阶段二：教学与来源核对

固定阶段一记录后，再提供：学习目标、原材料、教师答案、映射表摘录及素材核验依据。

- 检查数学准确性、任务可完成性、信息首次揭示位置、前后衔接和材料证据链。
- 规划、三张映射表和 `approved` 标签同样可以被质疑；`approved` 只是待核对记录，不充当验收结论。
- 报告必须引用正文位置或可核对来源，不接受"总体良好"式结论。

返修后的再次学生试读若确有必要，应使用新的上下文；已读过完整材料的验收者可核查修复，但不能声称自己再次未见答案。

## 结论协议与返修接口

结论三选一，报告应短而可执行，并允许明确写出哪些地方合格（不设找错数量指标，不为表现工作量添加问题）：

| 结论 | 含义 | 主 Agent 的后续动作 |
|---|---|---|
| `PASS` | 已审范围内没有尚未处理的实质缺陷，必要证据足够。 | 继续装配与技术验收；不扩大解释为"整章教学效果已证明"。 |
| `REVISE` | 有证据表明正文或规划不能完成约定任务。 | 按缺陷归属退回写作或规划，完成后复验受影响范围。 |
| `NEEDS_EVIDENCE` | 学情、素材来源或可见版本等必要输入不足，无法作出相应结论。 | 补证据，或删除非必要且无法核验的材料；不将缺证据写成事实错误。 |

- 实质失败与证据不足同时存在时两类并列；补齐文件不自动消除正文失败。
- 数学错误、必须步骤缺前置、任务答案已被提前给出且没有新动作，才按实际影响返修；定义澄清、范例示范后的同类练习、仅点名未来定理，均不自动认定为泄露。
- 文风偏好和可选增强单列为建议，不阻止通过。
- 每条实质问题必须获得"修复并核验"或"给出依据后撤销"的结果之一；主 Agent 可对误报作有证据的裁决，但不能只写"已处理"或"综合考虑通过"。
- **返修预算**：默认成本为首次验收加一次针对性复验；同类问题仍存在时，先由主 Agent 检查入口设计、前置假设或冲突规则，再决定如何继续。预算耗尽不等于通过。

## 派发提示词模板 (Prompt Template)

```text
你负责独立审查一个数学学习片段，未参与其规划和写作。
目的：核对学生可见内容能否支持约定的学习任务，而非追求更多问题或更多修改。

阶段一输入：读者前置与用途、按阅读顺序排列的学生正文。
逐任务列出：所需动作、结果依据、尚缺信息；先提交此记录。
不要用你掌握的后续理论替学生补齐依赖。

阶段二输入：学习目标、原文、教师答案、映射及素材核验依据。
检查数学准确性、任务可完成性、信息首次揭示、前后衔接和材料证据。
规划和 approved 标签同样可以被质疑；报告应引用正文或可核对来源。

输出：所审版本与范围、前置假设、PASS / REVISE / NEEDS_EVIDENCE；
每个实质问题注明位置、证据、学习影响、负责环节和复验条件。
区分事实错误、证据不足、规则冲突和可选建议。不设找错数量指标。
不直接改写正文，不推断未观察到的学生表现或生成过程。
```

### 输入约束（主 Agent 派发时提供）

- 阶段一：读者前置假设 {{PREREQUISITES}}、学生可见正文 {{STUDENT_VISIBLE_TEXT}}（按阅读顺序，已剥离教师内容）。
- 阶段二：学习目标 {{OBJECTIVES}}、原文锚点 {{SOURCE_ANCHORS}}、教师答案 {{TEACHER_ANSWERS}}、映射表摘录 {{MAP_EXCERPTS}}、素材核验依据 {{EVIDENCE}}。
- 所审版本标识：{{VERSION_HASHES}}（所审文件的内容哈希或版本号）。

## 与技术检查的分工

确定性检查（`check_numbering.py`、`build.py`、`compare_versions.py`）与本验收**并列执行、互不替代**：

- 脚本负责编号、编译、泄露扫描、计数核对；脚本通过不代表教学验收通过，关键词扫描不视为教学合格。
- 本验收负责：读者能做什么、已被告知什么、仍不知道什么、首题还需要什么认知动作；最终应能从学生实际可见文本回答四件事——**研究什么对象；能立即做什么；发现了什么尚不能解释的现象；接下来的内容将解决哪一部分**。
- 允许先制作可审读草稿再验收；最终装配与交付前完成内容与技术两类验收即可，不要求"内容通过后才允许生成任何 TeX"的绝对顺序。
